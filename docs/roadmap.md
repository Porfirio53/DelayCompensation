# 分阶段实施路线

研究目标：面向动态通信与计算延迟的 TiRex-2 在线车辆状态预测补偿系统。先冻结可复核基线与单请求性能，再确定动态观测年龄、交付时刻目标和外部异步流式机制，最后研究模型状态复用。残差 Adapter 和模型训练暂缓。

本轮实现独立离线 speed 评估、完整预测轨迹边界、通用到达模拟/接收视图与 GPU 单请求计时。下面的在线机制属于后续工作。

## 1. 固定基线与 GPU 单请求性能

保持当前 256 点截取、padding=true、TTA 差分和 R²=0.6 配置、共享 checkpoint、当前源码指纹与官方对照身份。用五条插值轨迹作轻量开发回归，单独测 batch=1 输入处理到 CPU 轨迹返回的真实端到端延迟；区分加载、首次内核编译、预热和稳定样本。

后续手动完成 70010 查询的全量回放和至少 1000 样本的正式性能测量，并覆盖不同速度段、趋势差分触发和上下文长度。记录设备、驱动/软件版本、缓存状态、实际批量、P50/P95/P99、峰值显存和失败率，建立算法与性能各自的回归门槛。不能用批量耗时除以 batch size 评价单请求延迟。

## 2. 动态观测年龄与时钟域

先规定时间戳域和转换，再计算 AoI。当前离线回放假设理想共享时钟；准备语料在 CAN boot time 的整数微秒网格上做因果 ZOH，模拟接收时间也落在同一仿真域。这不构成真实时钟同步。

| 时间 | 域及含义 | 后续使用 |
|---|---|---|
| native sensor time | 源车传感器 boot time；ZOH 取值对应的原记录时刻 | 区分传感器年龄与发送网格年龄 |
| source time | 源端采样/发送网格时刻；当前为 25000 µs 网格 | 预测轨迹的时间基准 |
| receive time | 接收端记录包到达时刻，现场使用接收端单调时钟 | 只统计已到达包及通信情况 |
| snapshot/enqueue/start/delivery time | 接收端同一单调时钟 | AoI、排队、推理和交付计时 |

真实接入时需定义源时钟到接收端单调时钟的映射、offset/drift 更新与同步误差；不能直接相减两个设备的 boot time，也不能用可能校时跳变的墙上时间测排队/推理。接收端先将最后可见源时间换算到自己的时间基准，再计算观测年龄。源网格 AoI 与原传感器 AoI 分开记录，ZOH hold age 不应被遗漏或重复添加。

保留已观测的源时间、接收时间、native 时间、缺失位置及乱序状态。未来包的到达计划、最终是否丢包和未来速度只能由仿真/评分端使用。扩展现有固定、整段均匀延迟、相关抖动/长尾/丢包到达模拟时保持 trace 前缀与划分隔离规则，为 ZOH 语料和每个新场景重新生成官方对照。

## 3. 在交付时刻选值与评分

全部计时量采用同一接收端基准。若在入队快照时刻测量 `AoI_snapshot = t_snapshot - mapped(t_source)`，则实际结果交付跨度为：

```text
delivery_horizon = AoI_snapshot + (t_start - t_snapshot) + (t_delivery - t_start)
```

若在开始推理时重新计算 `AoI_start = t_start - mapped(t_source)`，排队时间已经包含其中，交付跨度为 `AoI_start + inference_to_delivery`。不能再加一次 queue。输入处理、GPU、取回与发布开销的计时边界要明确，统一端到端与子阶段的包含关系。

当前 `ForecastTrajectory` 以最后已到达源时间为锚，未来第 k 步是 `t_source + k × 25000 µs`，返回完整分位数轨迹。后续根据预计交付时间决定预测范围，实际完成后按真实交付时间选值。定义非网格交付时刻的插值规则，并针对同一时刻的真值评分，保留同步不确定性。

轨迹缓存须携带源基准、生成/交付时间、快照标识和有效范围；新轨迹到来时只覆盖其可解释的时间区间。若交付或发布时刻超出预测范围，先明确采用带过期标记的最后有效状态/保持值，并计入回退与年龄统计，不无限外推、不隐藏失败。当前 `value_at()` 会拒绝非网格或越界访问，尚未实现这些在线策略。

## 4. 外部异步接收、轨迹缓存与连续发布

建立持续接收/快照、单 GPU 推理 worker、预测轨迹缓存、独立状态发布器。推理优先处理最新快照：允许一个执行中任务和至多一个等待快照，更新时覆盖过时等待项，避免持续排队。到达包和最新源时刻变化时更新接收视图，不允许推理阻塞接收与发布。

状态发布器按自己的计划频率从有效轨迹选值；模型只按算力和快照变化频率更新。分别报告状态发布频率、模型预测更新频率、排队/推理/交付尾延迟、过期比例、丢弃快照数、模型失败/回退、交付及发布时刻误差。40 Hz 数据采样或计划发布不表示已经实现 40 Hz 模型推理。

先在可控仿真时钟和 ZOH held-out 语料中验收无未来泄漏、无持续积压、缓存范围有效、交付评分正确，再考虑真实通信接入及实际时钟同步。

## 5. 稳定后研究模型内部状态复用

论文 [TiRex-2](2607.01204v1.pdf) 的推理、流式处理、patch 和归一化讨论（3.2、3.3、4.2 及附录 C）说明循环结构具有状态复用潜力，但公开 `forecast()` 的当前实现每次执行完整输入变换与序列预测，没有接收并返回持久增量状态的公开边界。周期调用 `forecast()` 属于外部流式调度。

checkpoint 的 input/output patch 为 32 点，在本数据 40 Hz 下跨度 800 ms。需要一起审计：隐藏状态和辅助状态、未满 patch、patch 锚点及滑窗左 padding、输入归一化统计变化、趋势/TTA 差分状态和还原基准、迟到观测对已经处理 patch 的影响。源窗口移动一个点可能改变 patch 归属和整个输入变换，不能把旧 hidden state 无条件拼到新窗口。

先设计等价性检查：相同可见前缀的逐步路径与当前整段 `forecast()` 比较完整分位数轨迹；明确窗口淘汰、归一化变化、趋势切换和乱序到达时的失效/重算条件。等价与外部系统稳定后，再分别测满 patch 提交、部分 patch 重算及状态缓存的性能收益。新增加速必须同时核对精度、状态生命周期和交付误差，不提前承诺增量 API 或实时频率。
